# Architecture Overview

Storix is built upon a **Zero-Code-Modification**, fully AWS-native modular CloudFormation architecture. The platform decouples compute, storage, relational data, background queue operations, and generative AI search to achieve high availability, strict multi-tenant isolation, and FinOps efficiency.

![Storix Multi-Tenant AWS Cloud Architecture](/images/storix_system_architecture_master.png)

### Key Architectural Layers

## 2. Ingress & Edge Security (Block 1)

![Zoom Block 1 Ingress & Security](/images/zoom_block_1_ingress_security.png)

### Ingress Invariants & Security Boundaries
- **Route 53 Multi-Region DNS:** Automated active-passive failover between Primary Singapore (`ap-southeast-1`) and Secondary US East (`us-east-1`) based on Route 53 Health Checks.
- **AWS WAFv2 WebACL:** Attached to the public ALB, enforcing rate limits (2,000 req/5m), OWASP Top 10 Common Rule Sets, Known Bad Inputs, and SQLi protection.
- **Application Load Balancer (Dual-AZ):** Routes incoming HTTPS traffic directly to dedicated Target Groups based on tenant Host-Headers (`acme.png261.dev` → `tg-acme`), with HTTP/2 and TLS 1.3 enforced.
- **Zero Host-Header Tampering:** The ALB passes original host headers directly to containers without proxy mangling, aligning with Nextcloud trusted domain requirements.

## 3. Compute & Container Runtime (Block 2)

![Zoom Block 2 Compute & Container Runtime](/images/zoom_block_2_compute_container.png)

### Golden Container Baking & Cold Start Optimization
- **AWS Graviton ARM64 Native:** Container images are compiled multi-arch (`linux/arm64` primary, `linux/amd64` secondary), slashing vCPU and memory unit costs by 20%.
- **Zero Runtime Downloads:** Nextcloud Assistant (`v4.0.0`), OpenAI Integration (`v5.0.0`), and FullTextSearch (`v30.0.2`) are pre-baked into `/var/www/html/custom_apps/` during image build time, guaranteeing air-gapped readiness.
- **AWS SOCI Indexing:** Seekable OCI metadata layers allow ECS Fargate to begin task execution before the full container image is downloaded, achieving sub-15s boot times.
- **Sidecar Architecture:**
  - **Main Container:** Nextcloud 30 (Apache MPM event, PHP-FPM, OPcache tuned to 512MB).
  - **LiteLLM Sidecar:** Loopback proxy on `127.0.0.1:4000` translating OpenAI API requests to AWS Bedrock SigV4 calls.
  - **Apache Tika Sidecar:** Isolated document extraction service for PDF, Word, and Excel content parsing.
- **Dedicated Background Cron:** Amazon EventBridge triggers `php -f /var/www/html/cron.php` every 5 minutes in an independent task, preventing heavy background queues from contending with interactive web requests.

## 4. Data Storage & Relational Tier (Block 3)

![Zoom Block 3 Data & Storage Tier](/images/zoom_block_3_data_storage.png)

### Multi-Tiered Storage Architecture
- **Amazon RDS Proxy Connection Pooling:** Maintains warm pooled connections to PostgreSQL 16 / Aurora Global Database. Multi-tenant connection surges (e.g. 10 tenants × 20 Apache workers = 200+ connections) are multiplexed safely, avoiding database connection exhaustion.
- **Amazon EFS Configuration Store:** Dedicated POSIX Access Point per tenant (`/tenants/<tenant_id>/config`) with POSIX UID/GID 33 (`www-data`). Automatic lifecycle policies migrate inactive configs to EFS Infrequent Access (30 days) and Archive (90 days).
- **Amazon S3 Object Storage Vault:** Files are stored under tenant-scoped prefixes (`s3://<vault>/tenants/<tenant_id>/*`). S3 Intelligent-Tiering automatically optimizes costs between Frequent, Infrequent, and Archive Access tiers, combined with S3 Cross-Region Replication (CRR) for disaster recovery.
- **Amazon OpenSearch 2.11 Domain:** Dedicated tenant indices (`tenant_<tenant_id>`) indexing document content and metadata with BM25 inverted indexing and highlighter support.

## 5. Control Plane & FinOps Governance (Block 4)

![SuperAdmin Console AWS Architecture](/images/zoom_block_4_control_plane_finops.png)

### Control Plane Components
- **WebAuthn Biometric Passkeys:** Native Touch ID, Face ID, and FIDO2 authentication via Cognito User Pool with short-lived session tokens and `HttpOnly; SameSite=Strict` cookies.
- **Step Functions SAGAs:** Orchestrates tenant lifecycle operations (Provisioning, Suspension, Resumption, Deletion, DR Failover) with automated compensating rollbacks on partial failures.
- **DynamoDB Tenant Registry:** Stores tenant state, resource bindings, and OCC versioning tags with atomic conditional writes (`attribute_exists` and `version = :expected_version`).
- **Async OCC Command Engine:** Long-running maintenance tasks (`files:scan`, `db:add-missing-indices`) are executed asynchronously via `EXECUTE_OCC_ASYNC` and tracked via `CHECK_OCC_JOB`, eliminating 29s API Gateway timeout errors.
- **FinOps Scale-to-Zero:** Suspending a tenant scales its ECS Fargate task `desiredCount: 0`, detaches ALB routing, and frees database connection pool capacity, achieving **$0.00 idle compute cost**.

## 6. Generative AI & OpenSearch RAG Pipeline (Block 5)

![Zoom Block 5 GenAI & RAG Pipeline](/images/zoom_block_5_genai_rag.png)

### Hybrid RAG Flow
1. **Asynchronous Indexing:** When a file is uploaded to S3, EventBridge dispatches an event to Amazon SQS (backed by a Dead-Letter Queue).
2. **Document Ingestion:** A worker Lambda downloads the document stream, extracts text via Apache Tika, and indexes tokens into the tenant's isolated OpenSearch domain index (`tenant_<tenant_id>`).
3. **Lexical & Vector Search:** User search queries execute over OpenSearch BM25 inverted indexes for instant keyword hits and semantic embeddings via Amazon Bedrock Titan Text Embeddings.
4. **Context Grounding:** Relevant chunks are retrieved, filtered strictly by tenant boundary, and injected into the system prompt for Anthropic Claude 3.5 Sonnet on Amazon Bedrock.
5. **Private Localhost Communication:** All AI interactions flow exclusively over `127.0.0.1:4000` via IAM SigV4 authorization—no customer data ever leaves the AWS VPC perimeter.

## 8. Automated CI/CD Deployment Pipeline

![Storix Deployment Pipeline](/images/storix_deployment_pipeline.png)

The entire infrastructure, runtime container, and admin console are deployed autonomously through a 6-block pipeline with strict quality gates:
1. **Block 1: CI/CD & Authentication:** GitHub Actions authenticates to AWS via IAM OIDC STS (zero static access keys).
2. **Block 2: Build Artifacts & IaC Linting:** Docker multi-arch builds are executed, SOCI indices generated, and CloudFormation templates validated via `cfn-lint` and `checkov`.
3. **Block 3: Foundation & Storage:** VPC networking, security groups, KMS keys, S3 vault, EFS, RDS database, RDS Proxy, and OpenSearch are deployed.
4. **Block 4: Compute & Bootstrap:** ECS cluster, ALB listeners, target groups, and EventBridge scheduler cron rules are provisioned.
5. **Block 5: Control Plane:** Step Functions SAGA workflows, DynamoDB tenant registry, API Gateway, and CloudFront console distribution are deployed.
6. **Block 6: Delivery & QA:** 199 automated unit, security, property, and acceptance tests verify system invariants before routing live production traffic.

## 9. Zero-Cost Infrastructure Teardown & Destroy Process

![Storix Process Destroy](/images/storix_process_destroy.png)

To guarantee clean testing and absolute $0.00 idle cost, the platform implements an 8-stage automated destruction script:
1. **Safety Confirmation:** Strict confirmation parameter (`confirm_destruction=DESTROY`) prevents accidental execution.
2. **Tenant Scale-Down:** Active tenants are transitioned to suspended state, stopping running ECS tasks.
3. **ECS Service Deletion:** ECS services and task definitions are deregistered and drained.
4. **S3 Vault Purging:** Buckets are purged recursively, removing all versions, delete markers, and incomplete multipart uploads.
5. **EFS Teardown:** EFS Access Points and mount targets are removed.
6. **Database Teardown:** RDS Proxy and PostgreSQL clusters are deleted with automated final snapshots.
7. **Reverse Dependency Destruction:** CloudFormation stacks are deleted in reverse order (07 → 06 → 05 → 04 → 03 → 02 → 01) with dynamic retain-resources retry.
8. **Audit Verification:** Final scan ensures zero lingering resources and $0.00 continuing billing.

## 10. Multi-Tenant Isolation Model

<Warning>
  Cross-tenant access is strictly prohibited across all infrastructure layers. Every tenant strictly maintains:
  - **ECS Fargate Service**: `service-<tenant_id>` with dedicated target group and task definition.
  - **Database Catalog**: Dedicated `nc_<tenant_id>` catalog in PostgreSQL.
  - **EFS Access Point**: Scoped to `/tenants/<tenant_id>/config` enforcing POSIX UID/GID 33 (`www-data`).
  - **S3 Storage Prefix**: `s3://<vault>/tenants/<tenant_id>/*` guarded by IAM policies.
  - **OpenSearch Index**: Dedicated `tenant_<tenant_id>` index scoping all search queries.
</Warning>

### Container Task Layout

```
Fargate Task: nc-<tenant_id>
├── nextcloud (PHP-FPM / Apache)     → Port 80 (routed from ALB target group)
│   ├── Config mount                 ← EFS Access Point: /tenants/<tenant_id>/config
│   ├── Primary ObjectStore          ← S3 Gateway Endpoint: s3://<vault>/tenants/<tenant_id>/
│   ├── Search Indexing              ← Amazon OpenSearch 2.11: tenant_<tenant_id>
│   └── Database connection          ← Amazon RDS Proxy: proxy.<region>.rds.amazonaws.com
├── litellm-bridge (sidecar)         → 127.0.0.1:4000 (Localhost loopback only)
│   └── Amazon Bedrock SigV4 API     ← Claude 3.5 Sonnet & Titan Text Embeddings
└── apache-tika (sidecar)            → 127.0.0.1:9998 (Localhost loopback only)
    └── Document parser              ← PDF, Word, Excel text extraction
```

## 12. Strategic Engineering Roadmap

![Storix Gap Analysis & Strategic Roadmap](/images/storix_gap_roadmap_minimalist.png)

The Storix platform is architected across four progressive engineering phases:
1. **Phase 1 (Complete):** Core multi-tenant foundation, container-per-tenant isolation on Graviton ARM64, RDS Proxy connection pooling, 3-tier storage lifecycle, and FinOps scale-to-zero compute.
2. **Phase 2 (Complete):** SuperAdmin web console with WebAuthn biometrics, Step Functions SAGA orchestration, Async OCC command engine, and CloudWatch Synthetics 24/7 SLA monitoring.
3. **Phase 3 (Complete):** Amazon Bedrock GenAI integration, LiteLLM sidecar proxy, Apache Tika document extraction, Amazon OpenSearch 2.11 full-text search, and Multi-Region Disaster Recovery (Singapore ⇄ US East).
4. **Phase 4 (Future):** Kubernetes operator for hybrid multi-cloud, Active-Active multi-region read-write meshes, and autonomous AI-driven tenant self-healing agents.
